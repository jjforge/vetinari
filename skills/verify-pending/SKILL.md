# Verify pending-verify issues

Vetinari labels every issue it merges `pending-verify` (the config's `onIssueMerged: githubMarkPendingVerify(...)` handler). A merge is not a close: the issue closes only after someone checks the work on current `main`. This skill is that check. It decides which issues are **resolved**, closes those, and turns every gap into a filed follow-up, so nothing found is lost.

## The closing rule

An issue is **resolved** when, on current `main` (not just in its own commit):

- every acceptance criterion is met, **and**
- every "Desired behavior" bullet holds, read as the brief wrote it.

A behaviour bullet that doesn't hold keeps the issue open, even when every checkbox is met. Missing tests, polish and edge cases the brief never named become follow-ups and don't block closing. A maintainer's answer to a parked question (in the issue's comments, or `.vetinari.local/logs/archive/*.jsonl`) changes how its criterion is read; use the answer.

## Steps

1. **Collect.** `gh issue list --state open --label pending-verify`. For each, read the body and comments. Note any parked-question answers and any open blocked-by links (`gh api repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by`). An issue whose blocker is also in the batch is verified with it and can close only if its blocker closes. An issue blocked by anything else stays open untouched and is reported as waiting. Done when every issue is either in the batch or reported as waiting.

2. **Gates.** Run every `gates[].cmd` in `vetinari/config.mts` on `main`, in order, in the foreground, and read each to the end. Run them all, ignoring each gate's `when` scope: this checks the merged result, not one branch. A red gate stops the run: report it and close nothing.

3. **Verify.** Group the batch by area (shared files, one feature) into groups of at most five, and launch one verifier subagent per group, all in one message so they run in parallel. If the project defines an `issue-verifier` subagent (`.claude/agents/issue-verifier.md`), use it; otherwise launch general-purpose subagents briefed with [`verifier.md`](verifier.md). Pass each the issue numbers and anything from step 1 that changes how a criterion is read. Done when every issue has a verdict with evidence per criterion.

4. **Look.** Check what the verifiers list as needing a person: a page, a terminal UI, a rendered artifact. If the project documents how to run and inspect a fresh copy of `main` (its `CLAUDE.md`, `AGENTS.md` or `docs/agents/`), follow that. Done when every such item is either checked or listed as not checked.

5. **Decide.** Apply the closing rule to each issue. A verifier's GAPS verdict is a list to sort, not a decision: sort each gap into "breaks a behaviour bullet" (stays open) or "follow-up" (doesn't block).

6. **File follow-ups.** Group related gaps into a few issues, each labelled with its category and `needs-triage`, opening with `> *This was generated by AI while verifying merged work.*`, naming the issue it came from, and saying how it was found (test, probe, code reading). For an issue that stays open, file the fix as a `bug`, comment on the issue pointing to it, and set the issue blocked by the fix.

7. **Close.** For each resolved issue, one comment that opens with the same AI line, says what was checked (gates at the `main` commit, criteria, anything inspected by hand), and names any follow-up it produced; then remove `pending-verify` and close it.

8. **Report.** Closed, kept open and why, waiting on a blocker, follow-ups filed, what wasn't checked, and whether local `main` is pushed.
