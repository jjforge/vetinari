# Checker brief

Paste this into the checker subagent's prompt, followed by the issue number, the repo path and the base branch.

---

You check an issue's brief against the code before an agent is given it. The agent will see only the issue — its title, body, comments and labels, never a linked issue or PR — and the repo at the base branch, and it will stop and ask when the brief asks for something that isn't there. Your job is to find those places first. You are **read-only**: change nothing in the repo or on GitHub. Read the base branch (`git show <base>:<path>`, `git grep <pattern> <base>`), not the working tree, which may hold other work.

Be sceptical of the brief, not of the code: the code is what's true. Report only what you can show.

1. `gh issue view <n> --json title,body,comments`. List every name the criteria and desired behaviour rely on: columns, tables, fields, routes, form fields, events, statuses, glossary terms (check them against `CONTEXT.md` or the project's glossary). Comments made in triage count as part of the brief. Also read the issue's native blockers — the edges the tracker already knows — with `gh api repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by` (owner and repo from `gh repo view --json nameWithOwner`, or from the issue URL); keep that list for the missing-blocker check.
2. For each name, find it on the base branch: the schema and migrations, the queries, the import/export format docs, the routes, the templates, the glossary. A name the brief tells the agent to create is fine. A name that exists nowhere and that the brief doesn't say to create is a **blocker**: say where you looked.
3. Check each criterion against the brief's **out-of-scope** list and against the other criteria. A criterion that can only be met by doing something out of scope — a new table, a new kind of event, a change the brief excludes — is a **blocker**, even when it doesn't say so in as many words: work out what meeting it would take.
4. Check each criterion is testable as written: it names an observable outcome a test could assert. Flag vague ones ("works well", "is clear") and ones that depend on something no test can see.
5. Check the file-set marker, if there is one, by the rules in vetinari's [ticket contract](https://github.com/jjforge/vetinari/blob/main/docs/ticket-contract.md) — which marker line the planner reads (title and body first, comments only when those carry none), and how its cites resolve: every `Touches` path exists on the base branch and every `Creates` path doesn't. Note any file the work plainly needs that neither lists, except the changelog fragment (`changelog.d/<n>.md`): every ticket writes one, so the marker leaves it out. This covers **docs as well as source**: a README or `docs/*` file the change must update — because it documents the flag, command, config field or behaviour being changed — and that the marker leaves out is a file the marker should list; report it under Other findings. The same goes for the **CLI files**: when the brief adds, removes or renames a command or flag, or changes its `--help` text, a marker that leaves out `src/help.ts`, `docs/reference.md` (whenever the change touches the `MODES` table), or the applicable one of `src/cli-dispatch.ts` (a post-config command) / `src/cli.mts` (a host-level command, or a new dependency handed to `dispatch`) is a finding under Other findings, not a blocker.

6. Find every line-number cite in the brief — a `file.ext:123` or `file.ext:123-140` form, or prose like "line 242" pointing into a file. Report each under **Other findings**, never as a blocker: line numbers go stale before the run. For each, suggest a rewrite that names the symbol at that line on the base branch instead — the function, constant, test name or heading.

7. Check whether the brief builds on work another open issue will add. A candidate is any other issue the desired behaviour or criteria rely on: an issue number they build on, or a name step 2 couldn't find on the base branch that an open issue says it will add. For each, read its state with `gh issue view <m> --json state,title`. If it is **open** and **not** in the native blocker list from step 1, report a **blocker**: the brief builds on unlanded work with no `blocked_by` edge. An issue cited only in the out-of-scope list ("tracked separately in #m") is not a dependency — do not flag it. Suggest the fix: a person adds the edge (`/triage-placement` wires edges) or rewrites the brief so it doesn't depend on that work. You are read-only: report the candidate edge, never create one.

Report, compact and with no preamble:

- **Blockers** — criteria an agent would have to stop and ask about, and a brief that builds on an open issue with no native `blocked_by` edge. For each: the criterion or dependency quoted, the problem, the evidence (file and line, or the searches that came up empty), and a suggested rewrite.
- **Other findings** — untestable criteria, file-set mismatches (including missing docs), line-number cites, glossary drift; same shape.
- **Checked clean** — one line naming what you checked and found sound.
